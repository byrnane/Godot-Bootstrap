# Варианты шаблона

Репозиторий содержит только шаблон. Каждая игра развивается в отдельном репозитории после клонирования выбранной ветки.

| Ветка | Состав | Viewport и фильтрация |
| --- | --- | --- |
| `main` | Общие сервисы, UI и нейтральные Control-заглушки | 1280×720, canvas_items, linear |
| `3d` | Node3D, камера, свет, модели, коллизии, Jolt, Cyclops, Blender → GLB | 1280×720, canvas_items, linear |
| `2d` | «Лесной хранитель»: платформер, аренный шутер, головоломка | База 1280×720, canvas_items, expand, linear; fullscreen |
| `2d-pixelart` | Технический 2D-пример на пиксельной сетке | 640×360, viewport, integer, nearest |

Во всех ветках: Godot 4.7.2, Compatibility, Windows/Web и сохранение пропорций. В `2d` первый запуск полноэкранный, оконный размер 1600×900; остальные варианты сохраняют стартовое окно 1280×720.
Godot AI общий. Cyclops и его export plugin входят только в `3d`.
Общие идентификаторы сцен и формат SaveData v3 одинаковы. Игровые данные варианта находятся в `game_data`. Путь игровой сцены — `features/gameplay/gameplay.tscn`, уровней — `features/levels/level_a.tscn` и `level_b.tscn`.

В `2d` режимы загружаются внутри единого gameplay. Пути A/B остаются совместимыми входами в первые два уровня платформера. Пример и управление: `docs/2D_EXAMPLE.md` в ветке `2d`.

## PixelArt и UI

В PixelArt низкое разрешение применяется ко всему проекту, включая меню и HUD.
Ветка получает общие UI-компоненты и контракты из `main`. Текущая нейтральная тема рассчитана на 1280×720 и пока может выходить за экран при 640×360. Пиксельное оформление и адаптация композиции — отдельная задача.
Общие правила тем и компонентов: [UI_FRAMEWORK.md](UI_FRAMEWORK.md).
При целочисленном масштабировании свободное место окна заполняется полями; растягивать изображение дробно для заполнения окна не нужно.

## Развитие шаблона

**Основная разработка ведется в `main`. Это единственный источник общей логики шаблона.**
Общие функции и исправления, сервисы, UI-поведение, контракты и инструменты сопровождения развиваются здесь.

Все три варианта ответвлены непосредственно от `main` и зависят от его базы, а не друг от друга.
В вариантах меняются настройки проекта и рендера, особенности представления, мировые сцены, примеры, ресурсы и дополнительные аддоны.
Вариант расширяет общую базу, сохраняя ее поведение. Отдельные версии общих сервисов, собственная логика сохранений или обход общего flow в вариантах не допускаются.
Общая база не должна обязательно зависеть от ресурсов и аддонов конкретного варианта.

После завершения общего изменения обновите все три варианта. Перед объявлением варианта актуальным он должен содержать принятые изменения `main`.
Перенос закоммиченных обновлений:

```powershell
git switch 3d
git merge main
git switch 2d
git merge main
git switch 2d-pixelart
git merge main
```

Если ветка уже открыта в другом worktree, выполняйте merge в нем (`git -C <путь> merge main`), а не пытайтесь повторно переключить ее здесь. Пути показывает `git worktree list`. Незакоммиченные изменения merge не переносит; текущее состояние UI описано в [READINESS.md](READINESS.md).

При доработках запускайте только проверки затронутого поведения по [TESTING.md](TESTING.md).
Не повторяйте общий набор на всех ветках только из-за merge. Отдельный smoke варианта нужен, если затронуты его сцены, ресурсы, настройки или аддоны.
Установка аддонов и импорт нужны только при их отсутствии или изменении. Для обновления только документации запуск Godot не нужен.
При конфликтах сохраняйте одновременно общие изменения `main` и параметры варианта из таблицы. Не заменяйте целиком общий файл старой вариантной копией ради устранения конфликта.
Не вливайте целиком вариант обратно в `main`: вместе с общим исправлением туда попадут его мир и настройки.
Если общий дефект найден в варианте, исправляйте его в `main`, затем обновляйте варианты. Если исправление уже сделано в варианте, выделите общие файлы в отдельный коммит и перенесите его в `main`.

Во всех вариантах сохраняйте gameplay/HUD-контракты, scene IDs, общие сценарии переходов, сохранений, настроек, ввода и локализации.
Проверка включения актуальной базы, например для `3d`: `git merge-base --is-ancestor main 3d` (успех — код 0).

```powershell
pwsh -File scripts/install_addons.ps1
godot --headless --editor --path . --import
$env:GAME_TEMPLATE_VARIANT = git branch --show-current
pwsh -File scripts/run_smoke.ps1 -Headless
Remove-Item Env:GAME_TEMPLATE_VARIANT
```

Команды выше нужны при первичной подготовке варианта; это не обязательный прогон после каждой правки.
GitHub Actions не используются. Для новой игры на произвольно названной ветке переменная не нужна.
Копии игр обновления шаблона автоматически не получают.

## Выбор для новой игры

Перед созданием игры выберите `3d`, `2d` или `2d-pixelart` по типу проекта и клонируйте именно эту ветку.
`main` подходит, если нужна только общая инфраструктура и вы сами подготовите игровой мир.
Далее игра развивается в своем репозитории: замените `origin`, обновите README и инструкции `AGENTS.md` под игру.
Правила сопровождения четырех веток относятся к шаблону; повторять этот набор веток в каждой игре не требуется.
Пошаговое начало работы: [START_HERE.md](START_HERE.md), затем [BOOTSTRAP_CHECKLIST.md](BOOTSTRAP_CHECKLIST.md).

## Локальные файлы

`.local`, `.godot`, `builds`, установленные сторонние аддоны и локальная конфигурация MCP не входят в Git.
При переключении веток установленные игнорируемые аддоны остаются на диске: используйте отдельные клоны для вариантов либо перенесите ненужный аддон за пределы проекта.
Установщик сохраняет существующие локальные файлы и не удаляет чужие данные.
Для новой игры настройте MCP на ее папку отдельно.

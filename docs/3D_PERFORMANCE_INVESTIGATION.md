# Сбой отображения 3D-прототипа — 25 октября 2026

## Статус

**После перехода на Mobile/Direct3D 12 владелец подтвердил нормальную работу
редакторского запуска и обновленного Windows EXE. Web еще не принят.**

Точный механизм первоначального сбоя не установлен. До смены конфигурации
владелец подтвердил тяжелые тормоза после начала игры и в `RetroPrototype.exe`,
и при запуске из редактора. В одном из диагностических запусков окно оказалось
прозрачным при работающем звуке и захваченном курсоре; одновременно тормозила
система. После завершения игры обычная работа сразу восстанавливается.

Внутренний FPS Godot при этом мог показывать сотни кадров в секунду.
Этот счетчик не принимается как доказательство плавного изображения на мониторе.
Прежние функциональные проверки и графическое прохождение не подтверждают
работоспособность обычного запуска на машине владельца.

После пересборки владелец самостоятельно запустил игру из редактора и сообщил:
«все было отлично вроде», затем проверил обновленный EXE: «тоже нормально».
Это подтверждает устранение наблюдавшегося тяжелого торможения в двух обычных
точках запуска по наблюдению владельца. Полный маршрут и Alt-Tab этим сообщением
отдельно не подтверждены.

Практический вывод: смена графического пути устранила наблюдавшийся сбой на этой
машине. Одновременно заменены renderer и графический API, поэтому вывод о точном
дефекте OpenGL, Godot, NVIDIA или Windows не доказан. Сбой представления кадров
остается объясняющей гипотезой, а не установленной внутренней причиной.

## Внесенное исправление конфигурации

По просьбе владельца перебор запусков и дальнейшие замеры остановлены.
Ветка `3d` переведена с Compatibility/OpenGL на Mobile renderer; для Windows
явно выбран `rendering/rendering_device/driver.windows="d3d12"`.
Это заменяет графический API и путь представления окна. Лимит 60 FPS не вводится,
личные настройки VSync и Windows не меняются.

Основание выбора: [Godot рекомендует Direct3D 12 для Windows начиная с 4.6](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-property-rendering-rendering-device-driver-windows),
а Mobile подходит для простых 3D-сцен на современном desktop. Это конкретная
замена проблемного графического пути, а не доказанная локализация дефекта внутри
OpenGL или драйвера. Нормальную работу обычного запуска новой сборки подтвердил владелец.

Уже открытый редактор сохраняет прежний renderer до перезапуска. Новый EXE
получает конфигурацию при сборке. Агент не запускает игру автоматически.

Windows EXE пересобран штатным headless-экспортом, код завершения 0, без ошибок
и предупреждений в финальном журнале `.local/retro-prototype/export-windows-d3d12.log`.
Результат — `builds/windows/RetroPrototype.exe`; предыдущий EXE сохранен
в `.local/retro-prototype/RetroPrototype-before-d3d12.exe`.
Сам экспорт подтверждает только сборку; нормальное отображение затем подтвердил владелец.
Временный `run_perf.ps1` заблокирован явным отказом перед запуском процесса.

## Подтвержденные факты

- Windows 11 Pro, build 26300; RTX 4080 SUPER, NVIDIA 621.01; монитор около 240 Гц.
- Оба проблемных варианта запуска использовали Godot 4.7.2 и Compatibility/OpenGL.
- В сохраненных настройках владельца: оконный режим, VSync включена.
- В игровом журнале проблемного EXE есть версия и выбранный GPU; ошибок нет.
- В проверенном интервале системного журнала нет связанных записей о сбросе
  дисплейного драйвера. Это не исключает сбой отображения или драйвера.
- После завершения диагностических процессов GPU вернулась к обычной небольшой
  нагрузке; игровых процессов, оставленных этим исследованием, нет.
- CPU/physics-показатели диагностического сценария не объяснили видимые
  секундные задержки. Загрузка GPU сама по себе не устанавливает причину.
- Ограничение 60 FPS не принято как исправление. Один запуск владелец назвал
  плавным, другие — нет; короткие последовательные запуски и задержки сообщений
  не дают надежно связать все наблюдения с конкретной строкой эксперимента.
- В последнем инструментированном запуске подтверждены `max_fps=0`,
  `vsync_mode=0`, около 350–380 внутренних FPS в сцене. Это не подтвердило
  нормальное отображение: владелец сообщил о тяжелом сбое одного из последних
  запусков. VSync нельзя объявлять установленной причиной.

После этих сообщений графические запуски остановлены. Постоянные настройки
проекта, личный `settings.cfg`, драйвер и Windows в ходе диагностики не менялись.

## Что изучено

[Рекомендации Godot по jitter/stutter/input lag](https://docs.godotengine.org/en/stable/tutorials/rendering/jitter_stutter.html)
рассматривают в том числе 240, 360 и 480 Гц. Высокая частота монитора сама по себе
не означает несовместимость с движком. Рекомендованный лимит ниже VRR-границы
касается задержки и синхронизации; это не объяснение прозрачного окна и тяжелого
системного торможения.

[Штатные Profiler и Visual Profiler](https://docs.godotengine.org/en/stable/tutorials/scripting/debug/debugger_panel.html)
разделяют скриптовую/физическую работу и CPU/GPU-стоимость рендера. Изменять
геометрию, освещение или renderer следует после определения соответствующего
узкого места. Выбор Compatibility для простой 3D-сцены сам по себе допустим:
[обзор рендереров](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html).

Для проверки расхождения между внутренними кадрами и изображением нужен
отдельный замер представления кадров Windows. [PresentMon](https://github.com/GameTechDev/PresentMon)
измеряет CPU/GPU/display timings через ETW, поддерживая OpenGL. Его документация
указывает ограничения точности некоторых CPU/GPU-показателей для OpenGL и HAGS;
неподдерживаемые значения нельзя трактовать как измеренный ноль.

## Подготовленная диагностика

Локальные файлы находятся в `.local/retro-prototype/perf/` и исключены из Git.
`perf_probe.gd` и `run_perf.ps1` служат временными инструментами исследования;
их автоматическое начало игры сейчас **не использовать**. В них были отдельные
копии настроек и внешний watchdog, но этого оказалось недостаточно для безопасной
и достоверной визуальной приемки.

Подготовлен портативный `PresentMon-2.6.0-x64.exe` из официального релиза.
SHA-256 проверен по метаданным релиза:
`b2a706bc6ad475749e3b7e3409263aa1e6906d45bdcf993f6dbc0f660188f1af`.
Подпись Intel Corporation действительна. Установщик, служба и оверлей не ставились.

Двухсекундная попытка записи только уже открытого редактора завершилась отказом
ETW в доступе, exit code 6. Текущий процесс не имеет административного токена.
Штатный WPR также доступен, профили GPU и DesktopComposition присутствуют;
активной записи WPR нет.

После разрешения владельца выполнен один запрос UAC и трехсекундная запись
PresentMon на уже открытом редакторе. Процесс завершился с кодом 0, но CSV
с кадрами не появился; измеренных данных для диагноза это не дало.
Дальнейшая диагностика остановлена по просьбе владельца. PresentMon и игровые
диагностические сценарии автоматически не запускать.
